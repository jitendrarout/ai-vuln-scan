# AI Code Vulnerability Pattern Catalog

A documented taxonomy of vulnerability patterns specifically associated
with AI-assistant-generated code, distinct from general-purpose CWE
categories in that each entry here describes *why* AI assistants tend to
produce it, not just what the vulnerability is.

This catalog is versioned independently of the scanner implementation —
new patterns can be proposed and documented here even before detection
rules exist for them, and the catalog is citable on its own.

---

## AIVP-001 — Hardcoded Secret in Example/Placeholder Form
**Why AI produces this:** Assistants generate a plausible-looking example
credential to make a code sample runnable/demonstrable. The example
string is frequently copy-pasted into real code without being swapped
for an environment variable reference.
**Detection:** Known-format regex matching (AWS, Stripe, GitHub token
formats) plus entropy scoring on secret-like variable assignments.

## AIVP-002 — Unparameterized Query Construction
**Why AI produces this:** The most natural-looking way to explain "build
a query with this variable" in a code sample is string interpolation.
Parameterization requires an extra, less obvious step that isn't always
included unless explicitly prompted for.
**Detection:** Pattern matching on query-like function calls containing
template-literal/f-string interpolation of a SQL keyword block.

## AIVP-003 — Shell Command Built by String Interpolation
**Why AI produces this:** Same root cause as AIVP-002 — `exec("cmd " + arg)`
reads naturally in an example; `execFile()` with an argument array is
correct but less commonly what gets generated by default.
**Detection:** Pattern matching on shell-execution calls with interpolated
or concatenated strings.

## AIVP-004 — Permissive Default Configuration
**Why AI produces this:** A wildcard CORS origin, disabled TLS
verification, or debug mode "just works" in a demo and removes a class
of setup friction from the sample. The hardened equivalent requires
config the assistant doesn't have (real allowed origins, a real cert),
so it's often omitted rather than stubbed insecurely.
**Detection:** Direct pattern matching on known insecure config flags.

## AIVP-005 — Weak Cryptographic Primitive in a Security Context
**Why AI produces this:** MD5/SHA1 and `Math.random()` are the
first/simplest hashing and randomness functions most models associate
with generic "hash this" or "generate a random string" requests, and the
distinction between "fine for a checksum" and "unsafe for a password or
token" isn't always surfaced unless the prompt specifically asks about
security context.
**Detection:** Pattern matching on weak-primitive calls near
security-relevant variable names.

## AIVP-006 — Inconsistent Authorization Across Near-Identical Routes
**Why AI produces this:** When an assistant generates several similar
route handlers in sequence (often across separate prompts/edits), the
first is generated carefully with the full pattern, including auth
middleware; later ones — generated as "add another route like the
others" — sometimes drop a step in an otherwise-repeated pattern. This
is a distinctly AI-flavored bug: humans copy-paste and are more likely
to preserve the full block; assistants regenerate and can drift.
**Detection:** Structural analysis across all route definitions in a
file — identify majority-applied middleware, flag routes missing it.

## AIVP-007 — Verbose Error Response Leaking Internals
**Why AI produces this:** Returning `err.stack` or a full traceback in
an HTTP response is the fastest way to make a demo's error handling
"work" and visible during development; the split between server-side
logging and a generic client-facing message is a production concern
that's easy to omit from a first-pass generation.
**Detection:** Pattern matching on error objects/stack traces passed
directly into response-sending calls.

## Contributing a new pattern

Open an issue or PR with:
1. A short description of the pattern and a minimal reproducing example
2. Why it's specifically associated with AI-assisted generation (not just
   "a bug that can happen") — ideally with a citation or reproducible
   prompt that reliably produces it
3. A proposed detection approach

Patterns are accepted into the catalog independent of whether a detection
rule exists yet for `ai-vuln-scan` itself — documenting the taxonomy is
valuable on its own.
